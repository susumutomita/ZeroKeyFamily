## ペルソナ

| ペルソナ | プロフィール | 状況 |
| --- | --- | --- |
| A: 佐藤良子（75 歳） | スマホ利用歴 1 年未満。文字入力が遅く、片手で電話を持ったまま操作できない。「署名」「検証」の語は日常語彙にない。 | 「息子」を名乗る電話で「会社のお金をなくした。30 万円を今すぐ送って」と泣きつかれている最中。 |
| B: 佐藤太郎（45 歳） | 働く息子。日中は会議が多く、スマホは机の上でサイレント。アプリは月に数回しか開かない。 | 会議中に母からの確認のお願いを受信する。 |

## 1. ウォークスルー（W-02 → W-05 → 結果）

### ペルソナ A: 良子（W-02 確認要求の作成）

1. **電話を切ってよいのか分からず固まる（最大のつまずき）。** 詐欺師は電話を切らせない。良子は「電話しながらアプリを開く」操作（通話画面からホームに戻る）ができず、アプリにたどり着けない可能性が高い。W-02 にもホーム（W-01）にも「電話をいったん切ってよい」という後押しがない。
2. **「送金先（必須）」の入力でつまずく。** 電話で聞いた銀行名・支店・口座番号を覚えていない。フリーテキスト 1 欄では何をどの順で書くのか分からず、聞き直すために詐欺師との通話時間が延びる（圧力を受ける時間が延びる）。
3. **「理由（必須）」で手が止まる。** 内容にはプリセット（「お金を送ってほしいと言われた」）があるのに、理由は自由入力。「相手が言ったこと」を書けばよいのか、「自分が確認したい理由」を書くのか分からない。
4. **「回答期限 [30 分 ▼]」を「お金を送る期限」と誤読しうる。** 詐欺師に「30 分以内って出てるだろ、早くしろ」と逆用される危険がある。
5. **送信ボタンが押せない理由が分からない。** 注意文は枠外に静的に出ているだけで、どの項目が未入力なのかを指していない。良子は「壊れた」と感じてアプリを諦め、電話の指示に戻る恐れがある。

### ペルソナ A: 良子（W-05 応答待ち）

6. **「お願いがちゃんと届いたのか」が分からず不安になる。** 「太郎さんの端末からの応答がありません」だけでは、送信失敗なのか、太郎が見ていないだけなのか区別できない。スマホ歴 1 年未満の良子は「自分の操作ミスで送れていないのでは」と疑い、再送を繰り返すか、諦めて電話の指示に従う。
7. **いつまで待てばよいかが画面にない。** 残り時間の表示がなく、「期限まで待つ」を押した後に何が起きるのかも不明。待っている間ずっと詐欺師の電話の圧力にさらされる。
8. **ボタンが 4 つ並び、選べない。** 「別の家族に確認する」「このお願いを取り消す」「困ったとき」「期限まで待つ」が同格で並ぶと、認知負荷の高い状況では選択を放棄する。特に「取り消す」は「取り消したら太郎にもう確認できなくなるのでは」という不安で押せない。
9. **「別の家族に確認する」を押すと入力をやり直しになる（仕様上の含意）。** 金額・送金先・理由をもう一度入力する体力は残っていない。
10. **電話を切る指示がここにもない。** 「急かされていませんか」は良い問いかけだが、次の行動（電話を切る・かけ直さない）まで言い切っていない。安全文言ガイド原則 4（行動の指示を曖昧にしない）の精神を W-05 にも適用してほしい。

### ペルソナ A: 良子（結果画面）

11. **W-04「同意の署名をしました」「署名日時」は専門用語。** 安全文言ガイドの言い換え表は「署名 → （人名）さんの端末による同意」と定めているのに、W-04 の主文と標準文言の両方に「署名」が出ている。正本文書間の不整合であり、良子は「署名って、はんこ？」と立ち止まる。
12. **W-06 検証失敗に行動指示がない。** 「応答の検証に失敗しました。安全のため、承認として扱いません。」は何が起きたのか・何をすべきか分からない。拒否・期限切れには「お金を送らないでください」があるのに、検証失敗（むしろ攻撃の兆候として最も危険な状態）にだけない。
13. **W-05 / W-05b の見出し記号「？」「✕」は読み上げで伝わらない。** アクセシビリティ機能利用者（テスト計画の補助対象）には文言だけが頼りになる。

### ペルソナ B: 太郎（W-03 受信 → 応答）

14. **気づけない。** 通知に金額を含めない方針（ロック画面漏えい防止）は正しいが、「確認のお願いが届いています」だけでは他の通知に埋もれる。太郎が気づかない 30 分の間、良子は W-05 で詐欺師の圧力に単独で耐えることになる。Phase 1 はプッシュ通知スコープ外だからこそ、「家族側が気づく速さ」が体験の最大の穴である。
15. **「拒否する」が母を拒絶するようで押しにくい。** 太郎は「身に覚えはないが、母を突き放すようで気が引ける」と感じ、放置（応答なし）に流れる。放置は最悪の結果（良子が W-05 で孤立）を招く。
16. **拒否した後の母の様子が分からない。** 「拒否は届いたか」「母は送金をやめたか」が太郎側に見えず、結局電話することになる。それ自体は望ましい行動なので、拒否直後の画面で電話を促すべきである。

## 3. 受け入れ基準のユーザー視点評価

### 評価

現在の 8 項目はプロトコルの安全性（改ざん・リプレイ・失効・回避経路）を網羅しており、「システムが嘘をつかない」保証としては適切である。一方で「ユーザーが正しく理解・行動・後悔からの回復ができる」ことを担保する基準が薄い。データモデルには `invalidated` 状態と `POST /api/requests/:id/cancel` が存在するのに、チェックリストに取り消し系の基準が 1 つもないのは穴である。

### 追加提案（チェックリスト案）

- [ ] **取り消しの競合**: 依頼者が取り消した要求は `invalidated` になり、取り消し後に到着した承認応答は成立しない（approved にならない）。
- [ ] **承認後の後悔（事後取り消し）**: W-08「まちがえて承認してしまった」に対応する API 経路が存在し、高リスク待機中（`high_risk_wait_until` 前）の承認は承認者・依頼者のどちらからも単独で取り消せる。
- [ ] **期限後応答の拒否**: 期限超過後に届いた署名付き応答は、署名が正しくても approved にならない。
- [ ] **確認済み表示の必須 3 要素**: 「確認済み」を返す API レスポンス / 画面が、誰の端末か・何に同意したか（金額・送金先・理由の再掲）・限界の注意の 3 点を欠かさない（安全文言ガイドの必須要素をテストで担保する）。
- [ ] **危険シグナル注意文**: 「今すぐ」を含む依頼・初送金先・深夜高額の各条件で、結果にかかわらず対応する注意文が表示される。
- [ ] **再確認の入力引き継ぎ**: 「別の家族に確認する」で金額・送金先・理由が引き継がれ、nonce と期限は新規発行される（旧 nonce の再利用は検証で拒否される）。
- [ ] **緊急停止の到達性**: すべての画面から「困ったとき」へ 2 タップ以内で到達でき、緊急停止は確認ダイアログ 1 回で発動する（ユーザビリティテスト T6 の前提を実装で固定する）。
- [ ] **未送達と未応答の区別**: 確認要求の送達（家族側が取得可能になったこと）と未応答を依頼者画面で区別できる（H-2 の前提となる API 表現を持つ）。

### ユーザビリティテスト計画への追加観点

- **T8（提案）: 承認直後に「やっぱり間違いだった」と気づくシナリオ。** 取り消し導線を 60 秒以内に発見できるか。「承認後の後悔」はテスト計画の最重要リスク 2 つ（確認済み誤解・応答なし誤認）に次ぐ第 3 のリスクとして扱うべきである。
- **T3 の測定追加**: 通話を切らずに（または切って）アプリへ到達できた率と所要時間。H-1 の文言改善の効果測定に使う。
