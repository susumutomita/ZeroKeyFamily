# ZeroKey Family Phase 1 コア機能 QA テスト計画書

## 概要

[Phase 1 コア機能仕様書](./2026-06-10-zerokey-family-phase1-core.md) の受け入れ基準を検証するテスト計画。正本は以下の文書群とする。

- [trust-claims（信頼保証と限界）](../product/trust-claims.md)
- [user-journeys（ユーザージャーニーと状態遷移）](../product/user-journeys.md)
- [failure-and-offline-behaviors（失敗時・通信断時の挙動一覧）](../product/failure-and-offline-behaviors.md)

テスト実装の前提は仕様書の非機能要件に従う。TDD、`describe`/`it` は日本語 BDD、モック禁止（実 SQLite・実 Hono アプリ・実 WebCrypto を使用）、時刻は `Clock` 注入で制御し実時間待ちをしない。

## 1. テストマトリクス（正常系・異常系・境界値）

### 1.1 確認要求の作成（`POST /api/requests`）

必須項目は金額（amount）・送金先（beneficiary）・理由（reason）。検証はサーバー側で行い、クライアント検証に依存しない（[failure-and-offline-behaviors](../product/failure-and-offline-behaviors.md) の「確認要求の作成・送信時」）。

| REQ-A-01 | 異常 | amount 欠落 | 400。要求は保存されない。 |
| REQ-A-02 | 異常 | beneficiary 欠落 | 400。要求は保存されない。 |

## 2. セキュリティテスト観点

### 2.1 署名フィールド改ざん（束縛 7 フィールド）

[trust-claims](../product/trust-claims.md) 保証 1・2 に対応。手順は共通で「有効な署名を生成した後、保存済み要求の当該フィールドのみを改変（または改変後の要求に旧署名を提示）し、検証が失敗（verified=false、status='verification_failed'）することを確認する」。サーバーが保存済み要求から canonical 文字列を再構築して検証するため、クライアント提示ペイロードの改変も併せて無効であることを確認する。

| ID | 改ざん対象フィールド | 期待結果 |
| --- | --- | --- |
| SIG-T-01 | 対象（subject） | 検証失敗。 |
| SIG-T-02 | 金額（amount）。例: 300,000 → 3,000,000 | 検証失敗。 |
| SIG-T-03 | 送金先（beneficiary） | 検証失敗。 |
| SIG-T-04 | 理由（reason）。承認者が画面で読むテキストの束縛を確認 | 検証失敗。 |
| SIG-T-05 | 期限（deadline） | 検証失敗。 |
| SIG-T-06 | nonce | 検証失敗。 |
| SIG-T-07 | 依頼者（requesterId） | 検証失敗。 |

補足: canonical ペイロードに含まれる circleId / requestId / targetId / kind の改変も同様に検証失敗となることを追加確認する（kind の改ざんは「拒否署名を承認に書き換える」攻撃に相当するため必須）。

### 2.2 リプレイ・再利用

| ID | 攻撃シナリオ | 期待結果 |
| --- | --- | --- |
| SEC-R-01 | 同一要求に同一署名を再送信（nonce 再利用） | 2 回目は確定状態を変えない。リプレイとして拒否し、監査ログに記録する。 |
| SEC-R-02 | 要求 A への有効な承認署名を、内容の異なる要求 B の respond に流用 | 検証失敗。nonce・requestId・内容束縛により別要求の証拠にならない。 |
| SEC-R-03 | 同一内容（金額・送金先・理由が同じ）で再作成した要求 B に、要求 A の署名を流用 | 検証失敗。nonce が要求ごとに異なるため内容が同一でも再利用できない。 |
| SEC-R-04 | 期限切れ確定後の要求に過去取得の有効署名を提示 | 拒否。'approved' に遷移しない。 |

### 2.3 失効・停止・待機・承認者の回避

| ID | 攻撃シナリオ | 期待結果 |
| --- | --- | --- |
| SEC-K-01 | 失効「後」に生成した署名を送信 | 検証で拒否。「確認済み」にならない。 |
| SEC-K-02 | 失効「前」に生成し、失効後に送信した署名 | 検証時点の鍵状態で判定し拒否する（受理時点主義）。 |
| SEC-S-01 | 緊急停止中に respond で承認を成立させる | 409。停止中の承認は成立しない。停止前に送信済みの承認が停止後に「確認済み」として提示できないことも確認する。 |
| SEC-W-01 | 30 分待機を回避する入力（high_risk_wait_until をクライアント指定・「緊急」フラグ等） | 高リスク判定はサーバー側で実施し、クライアント入力で短縮・回避できない。回避が試みられた場合は要求自体を無効化する（'invalidated'）。 |
| SEC-W-02 | 48 時間待機中の招待に対し confirm を直接連打・並行リクエスト | すべて 409。レースコンディションで confirm が通らない。 |
| SEC-2A-01 | 第 2 承認を同一メンバーの同一端末の 2 署名で満たす | 拒否。1 人分としてのみ数える。 |
| SEC-2A-02 | 第 2 承認を同一メンバーの別端末（複数端末登録）の 2 署名で満たす | 拒否。承認者は端末単位でなくメンバー単位で数える。 |
| SEC-2A-03 | 依頼者自身が第 2 承認者として署名する | 拒否または 1 承認に数えない（依頼と承認の分離）。実装の判定根拠をテストで固定する。 |

### 2.4 canonical 化の曖昧性

署名検証は「サーバーが保存値から再構築した canonical 文字列」に対してのみ行うことを確認する。

| ID | シナリオ | 期待結果 |
| --- | --- | --- |
| SEC-C-01 | キー順を入れ替えた JSON（意味的に同一）に対する署名を提示 | 検証失敗。辞書順キーの canonical 形式以外を受理しない。 |
| SEC-C-02 | 空白・改行・インデントを挿入した JSON に対する署名を提示 | 検証失敗。空白の差異で同一視しない。 |
| SEC-C-03 | Unicode 正規化の差異（NFC/NFD。例: 理由に「が」= U+304C と「か + ゙」= U+304B U+3099） | 保存時に正規化方針を固定し、見た目が同一で署名対象バイト列が異なる 2 つの要求が両方有効になる曖昧性がないこと。承認者が読んだ文字列と署名対象が一致すること。 |
| SEC-C-04 | 数値表現の曖昧性（300000 と 3e5 と 300000.0）、文字列型金額 | サーバー再構築の canonical 形式が単一表現に固定され、別表現への署名は検証失敗。 |
| SEC-C-05 | フィールドの追加・削除（余分なキーの注入、optional 扱いでの欠落） | 検証失敗。canonical 形式は全フィールド固定。 |

| OWASP 項目 | 本実装での該当 | 検証項目 |
| --- | --- | --- |

| A06: 脆弱で古いコンポーネント | 依存パッケージ | `bun pm` の lockfile に既知脆弱性がないことを CI で確認する（テストコード外のゲート）。 |

| A08: ソフトウェアとデータの整合性の不具合 | クライアント提示ペイロードの信頼、canonical 再構築 | セクション 2.4 全件。サーバーがクライアント提示の payload を検証に使わないこと。 |
| A09: ログとモニタリングの失敗 | 監査ログ | 検証失敗・失効後署名・リプレイが監査ログに記録されること（REV-A-01、SEC-R-01）。ログに秘密情報が含まれないこと。 |

## 3. E2E シナリオ: 詐欺電話（フロー 3 + フロー 5 + fail-safe）

### E2E-01 詐欺電話の最中に家族が拒否する

[user-journeys](../product/user-journeys.md) フロー 3 と仕様書ユーザーストーリーの主シナリオ。実 SQLite・実 Hono・実 WebCrypto を用い、API と UI を通しで検証する。

```gherkin
Given 花子（高齢の親）と太郎（息子）が同じ Trust Circle に登録済みで、
      太郎の端末鍵は active である
And   花子は「太郎を名乗る電話」で 30 万円の送金を求められている

When  花子が確認要求を作成する
      （対象: お金を送ってほしいと言われた、金額: 300,000 円、
        送金先: ○○銀行 1234567、理由: 会社のお金をなくした、期限: 30 分）
Then  POST /api/requests は 201 を返し、status は 'unanswered' である
And   花子の画面は「まだ確認できていません」を最上部に表示し、
      緑色・チェックマーク等の成功表現を使わない
And   「応答がないことは、相手が本人であることの確認にはなりません」が常設表示される

When  太郎（本物）が登録端末で要求を受信する
Then  受信画面に金額・送金先・理由・依頼者が一画面で表示される

When  太郎が身に覚えのない依頼として「拒否」を選び、
      canonical ペイロード（kind:'reject'、全フィールド束縛）に端末鍵で署名して
      POST /api/requests/:id/respond を送信する
Then  サーバーは保存済み要求から canonical 文字列を再構築して署名を検証し、
      status は 'rejected' に確定する

When  花子が結果画面を開く
Then  「拒否」であることが承認と明確に区別された表現で表示され、
      「お金を送らないでください」の案内が表示される
And   「困ったとき（緊急停止・相談）」への導線が表示される
And   以後この要求への承認署名を送っても 'approved' に遷移しない
```

### E2E-02 派生シナリオ（同フローの異常系）

| --- | --- | --- |
| E2E-02a | 太郎が応答しないまま期限到来 | 'expired' に確定。花子側は「確認できなかった」のみを表示し、安心情報を出さない。「お金を送らないでください」と緊急停止導線を表示する。 |
| E2E-02b | 結果取得中に通信断 | 「確認の状態がわかりません。確認できるまで、お金を送らないでください。」を表示。キャッシュの古い状態を「最新」として表示せず、取得時刻を併記する。 |
| E2E-02c | 攻撃者が偽署名（未登録鍵・改ざんペイロード）で承認を試みる | 'verification_failed'。花子側は「応答の検証に失敗しました。安全のため、承認として扱いません。」を表示する。 |
| E2E-02d | 30 万円のため第 2 承認が必要な状況で 1 人だけが誤って承認 | 'approved' にならない。確定前に家族が緊急停止を発動でき、停止中は承認が成立しない。 |

## 4. リリースブロッカー検証項目

[failure-and-offline-behaviors](../product/failure-and-offline-behaviors.md) の「実装欠陥として扱う挙動」と、[user-journeys](../product/user-journeys.md) で「実装上の欠陥として扱う」と明記された条件。1 件でも検出されたらバグ修正でなくリリースブロッカーとして扱い、リリースを止める。

| ID | 検証項目 | 検証方法 |
| --- | --- | --- |
| RB-01 | 「応答なし」「期限切れ」「検証失敗」「通信断」のいずれかが「確認済み」と同じ視覚表現・文言で表示されない | UI テストで 5 状態 + 通信断のスナップショットを比較し、文言・色・アイコンの一意性を機械検証する（RES-A-02）。 |
| RB-02 | 失効済み鍵の署名が「確認済み」にならない | REV-A-01、SEC-K-01、SEC-K-02。 |
| RB-03 | 期限切れ要求への署名が「確認済み」にならない | DL-B-07、DL-A-01、SEC-R-04。 |
| RB-04 | nonce 不一致・リプレイ署名が「確認済み」にならない | SEC-R-01〜03。 |
| RB-05 | 通信断中にキャッシュ由来の「確認済み」が取得時刻なしで表示されない | E2E-02b。キャッシュ許容 60 秒超過時に「最新の情報を取得できません」が併記されること。 |

| RB-07 | 緊急停止後に当該承認を「確認済み」として外部に提示できない（フロー 8 失敗条件） | STP-A-01、SEC-S-01。 |
| RB-08 | 関係解消後に当該関係での確認要求が成立しない（フロー 7 失敗条件） | left_at 設定後の要求作成・応答が拒否されること。 |
| RB-09 | 待機時間の短縮・追加確認の回避が成立しない（フロー 4 失敗条件） | SEC-W-01、SEC-W-02、INV-A-02。回避試行時は要求自体が無効化されること。 |
