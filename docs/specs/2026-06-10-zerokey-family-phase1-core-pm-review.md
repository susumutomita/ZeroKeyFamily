## 1. ユーザーストーリーの詳細化（ペルソナ別）

### ペルソナ定義

| ペルソナ | 説明 | 最優先の価値 |
| --- | --- | --- |
| P-A: 高齢の親（明子・74 歳） | 詐欺電話の主要な標的。スマートフォン操作は最小限。通話中の心理的圧力下で操作する。 | 操作の単純さと「確認できていない」ことの誤認しない表示。 |
| P-B: 別居の子（健一・45 歳） | 確認要求の主な応答者。日中は仕事中で即応できないことがある。 | 依頼内容の全体（金額・送金先・理由・依頼者）を一目で判断し、安心して拒否できること。 |
| P-C: 家族の世話役（美咲・40 歳） | Trust Circle の運営・招待・端末紛失対応・緊急停止を担う。複数の親族を見守る。 | 失効・停止・招待管理が単独で迷わず実行でき、悪用経路が閉じていること。 |
| P-D: 攻撃者（詐欺師） | 正規ユーザーではないが設計上の主要アクター。なりすまし・リプレイ・回避経路を狙う。 | （対抗目標）すべての回避経路がシステムで拒否されること。 |

### US-1: 確認要求の作成（P-A、フロー 3）

> 高齢の親として、詐欺電話の最中に「依頼内容」を本物の家族の登録端末で確かめるために、確認要求を送りたい。

受け入れ条件。

- 金額・送金先・理由・対象・期限を入力して送信すると、確認要求が `unanswered` 状態で作成される。
- 金額・送金先・理由のいずれかが欠けた要求は、UI のバリデーションに加えて API（`POST /api/requests`）が 400 で拒否する。クライアント検証を迂回した直接 POST でも同じ結果になる。
- 送信直後の依頼者画面は「まだ確認できていません」を最上部に表示し、緑色・チェックマークなど成功を示す視覚要素を使わない（フロー 5 の案内要件）。
- 同じ Trust Circle に属さない相手への要求は作成できない。

### US-2: 受信と承認・拒否（P-B、フロー 3）

> 家族として、身に覚えのない依頼を拒否し、その結果が依頼者に明確に伝わるようにしたい。

受け入れ条件。

- 受信画面は金額・送金先・理由・依頼者を一画面に表示する（最小 17pt 相当、スクロールなしで判読可能）。
- 承認はワンタップで完了せず、スライド相当の二段階操作を経る。
- 拒否は承認と同等に署名され、検証成功で `rejected` として依頼者に明示される。拒否理由の入力は必須にしない。
- 応答の署名ペイロードは対象・金額・送金先・理由・期限・nonce・依頼者・kind（approve / reject）を束縛する canonical JSON であり、サーバーは保存済み要求から再構築して検証する。
- 検証失敗時は `verification_failed` となり、「確認済み」とも「拒否」とも区別された表示になる。

### US-3: 端末紛失時の失効（P-C、フロー 6）

> 家族として、端末を失ったときに鍵を即時失効し、以後その鍵の署名が無効になるようにしたい。

受け入れ条件。

- `POST /api/devices/:id/revoke` で端末の status が `revoked` になり、`revoked_at` が記録される。
- 失効済み端末鍵による応答は、署名自体が数学的に正しくても `verification_failed` となり、`approved` に遷移しない（failure-and-offline-behaviors の「実装欠陥として扱う挙動」に該当するためリリースブロッカー水準で担保する）。
- 失効は復旧（新規鍵の生成と再登録）と独立して完了する。鍵の移行・エクスポートの経路を持たない。

### US-4: 緊急停止（P-C、フロー 8）

> 家族として、詐欺疑い・誤承認に気づいたら単独で緊急停止を発動したい。

受け入れ条件。

- Trust Circle の任意の 1 メンバーが `POST /api/circles/:id/stop` で停止を発動でき、理由の入力は必須でない（発動の心理的ハードルを下げる）。
- 停止中の circle に対する応答（`POST /api/requests/:id/respond`）は 409 で拒否され、承認は成立しない。
- 解除（`POST /api/circles/:id/release`）には発動者以外を 1 人以上含む 2 人の有効な署名が必要で、満たさない解除要求は拒否される。

### US-5: 遠隔招待の待機（P-C と P-D 対抗、フロー 2b）

> 世話役として、遠隔で家族を招待したいが、詐欺師が「家族」として入り込めない仕組みであってほしい。

受け入れ条件。

- remote 招待は `confirmable_at`（作成 + 48 時間）より前の confirm を 409 で拒否する。短縮オプションは存在しない。
- 待機中はどちらの当事者も取り消しできる（`cancelled`）。
- 対面 QR 招待（`kind: 'qr'`）は待機なしで相互確認に進める（推奨経路）。

## 2. 受け入れ基準のテストシナリオ展開（Given / When / Then）

仕様書の受け入れ基準 8 項目を、`bun test` の日本語 BDD（`describe` / `it`）に直結するシナリオへ展開する。すべて実 SQLite・実 Hono アプリ・実 WebCrypto を使い、時刻は `Clock` 注入で制御する。

### AC-1: 必須項目の API レベル強制

- シナリオ 1-1。
  - Given: 登録済みメンバー 2 名が同一 circle に属している。
  - When: 金額（amount）を含まない JSON を `POST /api/requests` に直接送信する。
  - Then: 400 が返り、`requests` テーブルに行が作成されない。
- シナリオ 1-2 / 1-3: beneficiary 欠落・reason 欠落についてそれぞれ同様に 400 と非作成を確認する。
- シナリオ 1-4。
  - Given: 同上。
  - When: amount に空文字列や 0 未満の値を送信する。
  - Then: 400 が返る（欠落と同等に扱う）。
- シナリオ 1-5。
  - Given: 同上。
  - When: 全必須項目を満たした要求を送信する。
  - Then: 201 が返り、状態は `unanswered` である。

### AC-2: 署名のフィールド束縛

- シナリオ 2-1。
  - Given: 有効な要求と、対象端末の WebCrypto 鍵ペアがある。
  - When: canonical ペイロード全フィールド一致の承認署名を送信する。
  - Then: 検証成功し `approved` になる。
- シナリオ 2-2。
  - Given: 同上。
  - When: amount / beneficiary / reason / deadline / nonce / requesterId / subject / targetId / circleId / kind の各フィールドを 1 つだけ改変したペイロードに署名して送信する（フィールドごとに 1 ケース、計 10 ケース）。
  - Then: いずれも検証失敗し `verification_failed` になる。`approved` には遷移しない。
- シナリオ 2-3。
  - Given: 同上。
  - When: クライアントが提示した改変済みペイロードと、改変前の要求に対する正しい署名を組み合わせて送信する。
  - Then: サーバーは保存済み要求から canonical 文字列を再構築して検証するため、クライアント提示ペイロードの内容にかかわらず結果が変わらない。

### AC-3: リプレイ（nonce・期限）拒否

- シナリオ 3-1。
  - Given: 要求 A への有効な承認署名が検証済みである。
  - When: 同じ署名を別の要求 B（nonce が異なる）への応答として送信する。
  - Then: 検証失敗となり、要求 B は `approved` にならない。
- シナリオ 3-2。
  - Given: 期限 30 分の要求がある。
  - When: `Clock` を期限後へ進めてから有効な署名で応答する。
  - Then: 要求は `expired` として扱われ、承認は成立しない。
- シナリオ 3-3。
  - Given: 確定状態（approved / rejected / expired）の要求がある。
  - When: 再度応答を送信する。
  - Then: 状態は変化しない（確定状態の上書き経路がない）。

### AC-4: 失効済み鍵の拒否

- シナリオ 4-1。
  - Given: 端末 D が `active` で、要求への有効な署名を作成できる。
  - When: D を失効させた後にその署名を送信する。
  - Then: `verification_failed` となり `approved` にならない。
- シナリオ 4-2。
  - Given: 失効前に作成・送信され `approved` 済みの応答がある。
  - When: 端末 D を失効させる。
  - Then: 過去の確定結果は改変されない（監査のため履歴保持）。一方、以後の新規署名は 4-1 のとおり拒否される。

### AC-5: 「応答なし」と「期限切れ」の状態分離

- シナリオ 5-1。
  - Given: 期限内・未応答の要求がある。
  - When: `GET /api/requests/:id` を呼ぶ。
  - Then: `unanswered` が返る。`approved` でも `expired` でもない。
- シナリオ 5-2。
  - Given: 未応答のまま `Clock` が期限を超過した。
  - When: `GET /api/requests/:id` を呼ぶ。
  - Then: 読み取り時に `expired` へ確定して返る。
- シナリオ 5-3（経路非存在の検査）。
  - Given: `unanswered` の要求がある。
  - When: 応答エンドポイント以外のあらゆる API 操作（取得・cancel・期限超過）を行う。
  - Then: どの経路でも `approved` に遷移しない。承認は有効署名の検証成功のみを経由する。
- シナリオ 5-4（UI）。
  - Given: 依頼者の結果画面で `unanswered` / `expired` を表示する。
  - When: 各状態を描画する。
  - Then: 「確認済み」と異なる文言・視覚表現（緑・チェックマーク不使用）であり、「応答がないことは、相手が本人であることの確認にはなりません」の注意文が常設される。

### AC-6: 高リスク条件の独立判定と回避不能

- シナリオ 6-1。
  - Given: 金額 100,000 円の要求を作成する。
  - When: 第 1 承認者の有効署名のみが揃う。
  - Then: `approved` にならず、第 2 承認者の署名が揃って初めて承認が成立する。境界値 99,999 円は第 2 承認不要であることも確認する。
- シナリオ 6-2。
  - Given: 過去に承認実績のない送金先への要求を作成する。
  - When: 必要な署名が揃う。
  - Then: `high_risk_wait_until`（+30 分）満了前は `approved` として確定せず、満了後に確定する。待機中の取り消しが可能である。
- シナリオ 6-3（重畳）。
  - Given: 10 万円以上かつ初送金先の要求を作成する。
  - When: 判定を行う。
  - Then: 第 2 承認と 30 分待機の両方が課され、片方の充足では承認が成立しない。
- シナリオ 6-4（回避経路なし）。
  - Given: 高リスク要求がある。
  - When: 「緊急」表示の付与、待機短縮を意図したパラメータ、待機前の確定 API 呼び出しを試みる。
  - Then: 待機は短縮されず、回避の試みは拒否される。サーバー側で高リスク判定するため、クライアントが判定結果を偽装できない。

### AC-7: 緊急停止の単独発動と 2 署名解除

- シナリオ 7-1。
  - Given: 3 人の circle で要求が `unanswered` である。
  - When: 任意の 1 メンバーが停止を発動する。
  - Then: circle が `stopped` になり、以後の有効署名の応答も 409 で拒否され `approved` にならない。
- シナリオ 7-2。
  - Given: 停止中の circle がある。
  - When: 発動者を含む 2 署名（発動者 + 他 1 人）で解除を要求する。
  - Then: 「発動者以外を含む 2 人」の条件は満たすため解除される。一方、発動者 1 人のみ・発動者の 2 端末による 2 署名は拒否される。
- シナリオ 7-3。
  - Given: 停止中の circle がある。
  - When: 1 署名のみ、または無効署名を含む 2 署名で解除を要求する。
  - Then: 解除されず `stopped` のままである。

### AC-8: 遠隔招待の 48 時間待機

- シナリオ 8-1。
  - Given: remote 招待を作成した（`confirmable_at` = 作成 + 48h）。
  - When: `Clock` が 47 時間 59 分の時点で confirm を呼ぶ。
  - Then: 409 が返り、招待は `confirmed` にならない。
- シナリオ 8-2。
  - Given: 同上。
  - When: `Clock` を 48 時間以降に進めて confirm を呼ぶ。
  - Then: `confirmed` になる。
- シナリオ 8-3。
  - Given: 待機中の remote 招待がある。
  - When: いずれかの当事者が cancel を呼ぶ。
  - Then: `cancelled` になり、以後の confirm は拒否される。
- シナリオ 8-4。
  - Given: qr 招待を作成した。
  - When: 直後に confirm を呼ぶ。
  - Then: 待機なしで confirm できる（remote のみが待機対象）。

## 3. 実装の優先度と依存関係

### 優先度の根拠

vision のガードレール指標（誤認 0 件・なりすまし成立 0 件・追加確認回避 0 件）と failure-and-offline-behaviors の「実装欠陥として扱う挙動」（リリースブロッカー）に直結するものを P0 とする。P0 はそれ単体で「署名がなければ確認済みにならない」というプロダクトの核を成立させる。P1 は P0 の上に乗る多層防御、P2 は登録経路の防御であり、開発用シードデータで代替しながら後続実装できる。

### P0（コアプロトコル。これなしでは価値が成立しない）

| 項目 | 内容 | 根拠 |
| --- | --- | --- |
| データモデルとマイグレーション | members / devices / circles / circle_members / requests / responses | 全機能の前提。 |
| Clock 注入 | 時刻依存ロジックの基盤 | 期限・待機・失効のテスト可能性の前提。後付けは全テストの書き直しを生む。 |
| 必須項目の API 強制（AC-1） | amount / beneficiary / reason 欠落の 400 | scope-and-non-goals で「緩和不可」とされた恒久ルール。クライアント検証依存はガードレール違反。 |
| canonical 署名と検証（AC-2, AC-3） | サーバー側再構築・フィールド束縛・nonce / 期限検証 | プロダクトの核。「返事の録音を別の依頼に流用できない」という差別化そのもの。 |
| 失効と検証の連動（AC-4） | revoke API と検証時の status 確認 | 失効済み鍵の署名通過は「実装欠陥」（リリースブロッカー）指定。検証ロジックと同時に作らないと回帰リスクが高い。 |
| 状態分離（AC-5） | unanswered / expired の区別、承認への単一経路 | 誤認 0 件のガードレール指標に直結。フロー 5 の失敗条件は「リリースを止める」と明記。 |
| 結果 5 状態の UI | 確認済み・拒否・応答なし・期限切れ・検証失敗の区別表示 | 視覚表現の混同は実装欠陥指定。API の状態分離と同時に画面の語彙を固定する。 |

### P1（多層防御。P0 の検証パイプラインに依存）

| 項目 | 内容 | 根拠と依存 |
| --- | --- | --- |
| 高リスク判定（AC-6） | 10 万円以上 → 第 2 承認、初送金先 → 30 分待機、条件独立判定 | 「追加確認回避 0 件」のガードレールに直結するが、単一承認の検証（P0）が正しく動くことが前提。第 2 承認は responses の複数行集計、待機は Clock に依存。 |
| 緊急停止・解除（AC-7） | 単独発動、停止中 409、2 署名解除 | 誤承認後の救済として被害低減に直結。解除の 2 署名検証は P0 の署名検証ロジックを再利用するため後続が効率的。 |
| 依頼者取り消し（W-05） | `POST /api/requests/:id/cancel` | フロー 5 の安全な案内（待つ・別の家族・取り消す）の選択肢を完成させる。 |
| 応答なし時の安全案内 UI | 注意文常設・詐欺注意導線・緊急停止導線 | フロー 5 の要件。緊急停止 API（同じ P1）への導線を含むため同時期に実装する。 |

### P2（登録経路の防御。コア検証フローから独立）

| 項目 | 内容 | 根拠と依存 |
| --- | --- | --- |
| 招待フロー（AC-8） | qr 即時確認、remote 48h 待機、取り消し | なりすまし侵入の防御として重要だが、P0 / P1 の開発・検証はシードデータの circle で進められるため後続可能。confirmable_at 判定は Clock（P0）に依存。 |
| 招待 UI（W 系画面） | QR 提示・リンク・待機中表示 | 招待 API の完成後。 |

### 依存関係の要約

```
Clock 注入 ──┬─> 期限判定（AC-3, AC-5） ──> 高リスク待機（AC-6）
             └─> 招待待機（AC-8）
データモデル ──> 必須項目強制（AC-1） ──> canonical 署名検証（AC-2, AC-3）
canonical 署名検証 ──┬─> 失効連動（AC-4）
                     ├─> 状態分離と結果 UI（AC-5）
                     ├─> 第 2 承認（AC-6）
                     └─> 停止解除の 2 署名（AC-7）
```

クリティカルパスは「データモデル → 必須項目強制 → canonical 署名検証 → 状態分離」であり、ここまでが通れば最小の縦切り（要求作成 → 承認 → 検証 → 結果表示）をデモできる。

## 4. スコープ外の再確認と将来差分

### 本仕様で実装しないもの（再確認）

scope-and-non-goals と仕様書のスコープ外宣言を再確認した。以下は本 PR に含めてはならず、混入はスコープクリープとして `/follow-up` で扱う。

- iOS / Android ネイティブアプリ、Secure Enclave / Android Keystore・StrongBox 統合、ストア配布。
- ZKP / MPC / FHE / ブロックチェーン Trust Registry（Phase 2 以降、導入には ADR 必須）。
- プッシュ通知、eKYC 等の本人確認外部連携、監視・SLO・バックアップ等の運用基盤。
- 恒久非目標: AI 真偽判定、秘密鍵のサーバー保管・署名代行、通話の録音・解析、暗号自作。本実装も WebCrypto の Ed25519 のみを使う。
- ユーザージャーニーのうちフロー 7（離脱・死亡・関係解消の 14 日異議期間）と、フロー 6 のうち家族申請による失効待機・バックアップコードは、仕様書の API 一覧に含まれていない。Phase 1 リファレンス実装の対象外として扱い、必要性が確定したら別仕様とする（下記の将来差分にも記載）。

### リファレンス実装（Web）とモバイル本実装の差分で将来必要になる項目

本実装は「ドメインロジックと API・Web UI の正本」であり、モバイル本実装への移行時に以下のギャップを埋める必要がある。各項目は ADR またはフォローアップ Issue の候補である。

| 領域 | リファレンス実装（Web） | モバイル本実装で必要になるもの |
| --- | --- | --- |
| 鍵保管 | WebCrypto + IndexedDB（exportable=false 相当の運用） | Secure Enclave / StrongBox での鍵生成・保管。非対応端末の登録拒否と案内（フロー 1 の失敗条件）。鍵のアテステーション（端末のセキュアハードウェア生成であることの証明）の要否判断。 |
| 署名時認証 | ブラウザ操作のみ | 生体認証 / パスコードを署名操作に必須として結合（フロー 3 の二段階操作の後半）。 |
| 本人確認 | 省略（メンバー登録のみ） | 登録時の本人確認フロー（フロー 1）。eKYC 連携の要否は別途判断。 |
| 通知 | ポーリング / 画面更新前提 | プッシュ通知（確認要求の到達・結果・緊急停止の全員通知）。「相手端末に到達」状態の検出はプッシュ到達確認に依存するため、状態遷移（送信済み → 応答なし）の精緻化が必要。 |
| 招待 | API 直接呼び出し相当 | QR コードの生成・読み取り（カメラ権限）、招待リンクのディープリンク / Universal Links、QR 有効期限と 24 時間無応答失効（フロー 2a の失敗条件）。 |
| 失効・復旧 | revoke API のみ | バックアップコード発行、他の自分の登録端末からの失効、家族申請による失効待機と本人異議（フロー 6）。 |
| 関係解消 | 未実装 | フロー 7 の離脱・死亡時解消、14 日異議期間、異議期間中の新規要求ブロックと進行中要求の無効化。 |
| 通信断 | ローカル前提 | failure-and-offline-behaviors の全項目（再試行 5 回・指数バックオフ、キャッシュ 60 秒と取得時刻表示、「最新の情報を取得できません」表示）。 |
| 緊急停止の範囲 | circle 全体の停止 | 「当該確認要求のみ」と「circle 全体」の停止範囲設定（フロー 8 の設定オプション）、相談窓口導線の実接続。 |
| しきい値設定 | 初期値固定（10 万円 / 30 分 / 48h） | 家族設定による厳格化（緩和は金額のみ可、送金先・未入力禁止は緩和不可）の設定 UI と検証。 |
| 運用 | なし | 監視・SLO・バックアップ・インシデント対応・サポート窓口（ロードマップのリリースゲート）。 |

### PM としての注記

- ドメインロジック（canonical 署名・状態機械・高リスク判定・Clock）はモバイル移行後も正本として再利用される前提のため、Web UI 層と分離した実装を Developer ロールに要請する。
- ガードレール指標（誤認 0 件・なりすまし 0 件・回避 0 件）に対応する AC-2 / AC-4 / AC-5 / AC-6 のテストは、退行検知のためリリース後も削除・緩和してはならない。
- 文言・視覚表現の検証（AC-5 のシナリオ 5-4）は機械検証が難しい部分を含むため、safety-copy-guide との突き合わせを QA ロールのレビューチェックリストに含めること。
