# 脅威モデル

ZeroKey Family が守る資産・想定する攻撃者・攻撃シナリオと緩和策の正本。設計済みの安全機構と未実装の安全機構を、明示した脅威に対する緩和策として位置づける。[Trust Claims](./trust-claims.md) の「保証しないこと」を残存リスクとして引き継ぐ。

正本 Issue: https://github.com/susumutomita/ZeroKeyFamily/issues/11

## 目的とスコープ

- 本文書は、確認サービスの中核（依頼内容への家族端末の署名検証）と、それを支える登録・失効・復旧・緊急停止の安全機構を対象とする。
- 対象範囲は本リポジトリのリファレンス実装（Hono バックエンドと Vite + React フロントエンド、WebCrypto Ed25519）とする。ネイティブアプリのセキュアハードウェア連携、ZKP / MPC / FHE、ブロックチェイン Trust Registry は [スコープと非目標](./scope-and-non-goals.md) のとおり対象外とし、該当箇所で前提として参照する。
- 独立した暗号レビューと侵入テストは外部プロセスであり、本文書は「外部検証で確認する項目」として境界を示すに留める。

## 資産

| 資産 | 説明 | 価値 |
| --- | --- | --- |
| 端末秘密鍵 | 各メンバーの登録端末が保持する Ed25519 秘密鍵。 | 署名の偽造可否を決める最重要資産。端末外へ出さない。 |
| 確認要求と署名 | 対象・金額・送金先・理由・期限・nonce・依頼者を束縛した依頼と、それへの端末署名。 | 「確認済み」の根拠。改ざん・流用・リプレイから守る。 |
| 確認履歴・家族関係 | 誰が誰にいつどの依頼をしたか、家族構成。 | プライバシー資産。パブリックチェインへ置かない。 |
| 端末セッション | 呼び出し元が当該メンバーの登録端末であることを示す認証状態。 | なりすましアクセスを防ぐ。現状は未実装（後述）。 |
| 監査証跡 | 安全操作の追記専用ログ。 | インシデント対応と事後追跡の根拠。現状は未実装（後述）。 |

## 信頼境界

| 境界 | 信頼の前提 | 主な脅威 |
| --- | --- | --- |
| 端末セキュアハードウェア | 秘密鍵は端末内で生成・保管し、認証成功時のみ署名する。 | OS レベルの侵害・ロック解除の強奪。 |
| クライアント（ブラウザ / アプリ） | canonical 形式の組み立てと表示文言を担う。 | 改ざんされた表示・中間者による要求差し替え。 |
| API（Hono） | 要求を保存し、保存済み要求から canonical を再構築して検証する。 | なりすましアクセス・認可不備・TOCTOU。 |
| データストア（`bun:sqlite`） | 要求・メンバー・端末・状態を保持する。 | サーバー侵害・データ改ざん・機微情報の漏えい。 |
| 通信経路 | TLS 前提。 | 中間者・リプレイ。 |

署名検証の核は、クライアントの善良性に依存しない。サーバーは保存済みの要求フィールドから canonical を再構築し、登録公開鍵で署名を検証するため、クライアントや通信経路を信頼しなくても「確認済み」の正しさが成立する。

## 想定する攻撃者

| 攻撃者 | 動機と能力 |
| --- | --- |
| 詐欺電話の発信者 | 声・電話番号・緊急性で高齢者に送金を急がせる。暗号鍵は持たない。 |
| 端末を奪取した第三者 | 端末を物理的に入手し、ロック解除手段の強奪を試みる。 |
| 家族内の悪意ある者 | 正規メンバーとして、正当な権限の範囲で不正に依頼・承認する。 |
| サーバー侵害者 | DB やサーバープロセスへの読み書きを得る。 |
| 通信経路上の攻撃者 | 中間者として要求・応答の傍受・改ざん・再送を試みる。 |

## 攻撃シナリオと緩和策

### 1. AI 音声・映像によるなりすまし送金

- シナリオ: 攻撃者が家族の声や映像を合成し、電話で高額送金を急がせる。
- 緩和策（実装済み）: 確認は声・電話番号・表示名を信頼の根にせず、対象メンバーの登録端末の署名でのみ「確認済み」とする。署名がなければ「確認済み」にならない。
- 残存リスク: 利用者が確認サービスを使わずに送金する運用上の隙。安全文言と緊急停止導線で緩和する。

### 2. 署名の流用・リプレイ・改ざん

- シナリオ: 過去の承認署名を別の依頼の証拠として使い回す、または通信経路で要求内容を差し替える。
- 緩和策（実装済み）: 署名は全フィールド（理由テキストを含む）を束縛し、nonce はサーバー生成、期限を強制する。サーバーは保存済み要求から canonical を再構築して検証し、改ざん・リプレイ・期限超過を拒否する。
- 残存リスク: なし（中核の保証範囲）。検証失敗は承認と区別した状態に確定する。

### 3. サーバー侵害による署名偽造

- シナリオ: サーバー運営者または侵入者が DB を操作し、偽の「確認済み」を作る。
- 緩和策（実装済み）: 秘密鍵をサーバーへ平文で預けない。サーバーは署名を検証できるが生成できない。署名は端末内の鍵でのみ作られる。
- 残存リスク: サーバーが状態表示を改ざんする可能性。クライアントは取得時刻を併記し、不明な状態を「確認済み」と表示しない（[失敗時挙動](./failure-and-offline-behaviors.md)）。

### 4. なりすましアクセス・認可不備

- シナリオ: 攻撃者が他メンバーの ID を申告し、名簿・履歴を閲覧し、承認・失効・緊急停止などを操作する。
- 緩和策（実装済み）: 読み取り API は家族コードのみの非メンバーに名簿・履歴を露出しないようメンバーシップを確認する。高リスク操作は対象メンバーと承認者の対応を検証し、検証の TOCTOU を避ける。
- 緩和策（未実装）: 現状の API はセッション認証層を持たず、申告されたメンバー ID を信頼する。各リクエストに端末鍵による署名付きセッションを課す必要がある。対応 Issue: https://github.com/susumutomita/ZeroKeyFamily/issues/13 。
- 残存リスク: セッション認証の実装までは、本人性の証明ではなく整合性確認に留まる。

### 5. 端末の奪取・乗っ取り

- シナリオ: 攻撃者が端末を入手し、ロック解除手段を強奪して署名させる。
- 緩和策（実装済み）: 端末失効（`POST /api/devices/:id/revoke`）により、失効後の署名を検証で拒否する。署名は端末の認証成功まで生成しない（ネイティブ前提）。
- 緩和策（未実装）: 紛失・機種変更後に新端末を安全に登録し直す復旧経路。家族の複数承認と待機時間を課すソーシャルリカバリーで、乗っ取り者による不正な端末追加を防ぐ。対応 Issue: https://github.com/susumutomita/ZeroKeyFamily/issues/14 。
- 残存リスク: 失効が間に合わない時間帯の署名。高リスク操作の待機時間で被害を緩和するが、検出は保証しない。

### 6. 脅迫下の承認（duress）

- シナリオ: 利用者が脅迫を受け、自由意思に反して登録端末で承認する。
- 緩和策（実装済み）: 高リスク操作の待機時間・複数人承認・緊急停止により被害を緩和する。緊急停止は単独発動でき、発動者以外を含む 2 署名で解除する。
- 残存リスク: 保証しない（[Trust Claims](./trust-claims.md) の限定緩和）。署名は端末の操作を示すのみで自由意思を示さない。

### 7. 家族内不正

- シナリオ: 正規メンバーが、権限の範囲で不正に依頼・承認する。
- 緩和策（実装済み）: 確認履歴の透明性と高額操作の複数人承認で抑止する。
- 緩和策（未実装）: 安全操作の追記専用な監査証跡により、事後の追跡可能性を高める。対応 Issue: https://github.com/susumutomita/ZeroKeyFamily/issues/12 。
- 残存リスク: 保証しない。複数人承認のしきい値内での共謀は防げない。

### 8. 登録時のなりすまし

- シナリオ: 攻撃者が家族になりすまして Trust Circle に参加する。
- 緩和策（実装済み）: 対面 QR 登録を推奨し、遠隔登録には 48 時間の待機時間と多経路確認を課す。片側のみ登録された中間状態を作らない。
- 残存リスク: 限定保証。公的な身元証明ではない。

### 9. 中間者・通信経路上の攻撃

- シナリオ: 攻撃者が要求・応答を傍受・改ざん・再送する。
- 緩和策（実装済み）: 内容束縛・nonce・期限により、改ざんとリプレイを検証で拒否する。TLS を前提とする。
- 緩和策（未実装）: 端末セッション認証により、傍受した要求の再送によるなりすましアクセスを塞ぐ（Issue 13）。

## 既存の緩和策と脅威の対応

| 緩和策 | 主に対応する脅威 |

| nonce（サーバー生成）と期限の強制 | リプレイ（2）・中間者（9） |
| 秘密鍵の端末内保管 | サーバー侵害（3） |

## 残存リスク

[Trust Claims](./trust-claims.md) の「保証しないこと」を残存リスクとして明示する。これらは優先度の問題ではなく、確認サービスの設計上の限界を表す。

- 脅迫下の承認。署名は自由意思を示さない。
- 端末乗っ取り。OS レベルで侵害された端末からの署名は防げない。失効による事後対応のみ提供する。
- 家族内不正。しきい値内での共謀は防げない。
- 登録時の身元。公的な身元証明ではない。
- 依頼内容の正当性。「確認済み」は依頼が安全・合法・賢明であることを意味しない。

## 外部検証で確認する項目

以下は本文書の範囲を超え、外部プロセスで確認する（[ロードマップ](./roadmap.md) のリリースゲート）。

- 独立した暗号レビュー（プロトコルと canonical 形式の健全性）。
- 侵入テスト（API・クライアント・運用基盤）。
- OWASP MASVS / MASTG 相当および NIST SP 800-63B 相当の要求への適合。
